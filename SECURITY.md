# Безопасность

Репозиторий **публичный**. Это допустимо только потому, что в коде нет ни одного
секрета — есть только имена переменных окружения. Проверено по всей истории
коммитов. Если хоть один ключ окажется в коде, его придётся считать
скомпрометированным и перевыпускать: удаление коммита не помогает, публичные
репозитории индексируются ботами за минуты.

## Что где хранится

| Секрет | Где живёт | Что даёт при утечке |
|---|---|---|
| `SUPABASE_SERVICE_KEY` | Vercel → Environment Variables | полный доступ ко всем данным пользователей, RLS обходится |
| `TELEGRAM_BOT_TOKEN` | Vercel → Environment Variables | управление ботом, подделка подписи владельца, подделка сессий |
| `SESSION_SECRET` (необяз.) | Vercel → Environment Variables | подделка сессии любого пользователя |

Ключи не должны появляться в `index.html`, в комментариях, в issue и в
переписке. Клиент в Supabase напрямую не обращается — в `index.html` нет ни
одного упоминания supabase, и это намеренно.

## Модель доступа

Три уровня, и ни один не опирается на присланный клиентом идентификатор.

**Публичное** — `GET /api/config`, `/api/markets`. Без авторизации, только
чтение неличных данных.

**Пользователь** — сессионный токен (`_session.js`). Выдаётся при входе, HMAC
на секрете, живёт 30 дней. Все личные эндпоинты (`/api/state`, `/api/nexus`,
свои заявки в `/api/payments`) берут идентификатор **из токена**, никогда из
запроса.

**Владелец** — подпись Telegram `initData` (`_telegram.js`). Telegram
подписывает её HMAC-ключом от токена бота; токен есть только на сервере,
поэтому подделать нельзя. Проверяются подпись, срок жизни 24 часа и совпадение
ID из подписанных данных. Закрыты: `POST /api/config`, `/api/admin`, список
заявок и `review` в `/api/payments`, `admin_credit` в `/api/nexus`.

Оба сравнения хешей — постоянного времени: обычное `===` выходит на первом
несовпавшем байте и по времени ответа выдаёт, сколько символов угадано.

Общий принцип: **невозможность проверить — это отказ, а не разрешение.** Если
на сервере нет `TELEGRAM_BOT_TOKEN`, админка и сессии закрываются, а не
открываются.

## Что было исправлено

Две дыры, обе подтверждены на живом продакшене до исправления.

**Права владельца определялись присланным ID.** `?admin=566501781` — а этот ID
публичная константа в `index.html`. Любой, кто открыл исходник, мог читать
выручку и список пользователей, **подтверждать чужие оплаты**, начислять баланс
NEXUS и включать режим обслуживания.

**`/api/state` не проверял вообще ничего.** `GET /api/state?user=<чужой id>`
отдавал чужие счета, баланс и заявки на вывод; `POST` их перезаписывал. То есть
посторонний мог выдать себе фандед-счёт или стереть чужой прогресс.

## База данных

RLS включён на всех таблицах (`users`, `user_state`, `trades`, `payments`,
`app_settings`) **без политик**. Это не упущение: весь доступ идёт через
`/api/*` по service-ключу, который RLS обходит по определению, а клиент в базу
не ходит. Пустой список политик здесь — самая строгая конфигурация: любой, у
кого окажется anon-ключ, не получает ничего.

Политики понадобятся только если появится прямой доступ из браузера.

## Что стоит сделать дополнительно

- **Ограничение частоты запросов.** Сейчас его нет: `/api/auth` и `/api/state`
  можно звать без ограничений. Для перебора это не страшно (подписи проверяются
  криптографически), но исчерпать лимиты Vercel и Supabase можно.
- **Защита ветки `main`** в GitHub: запретить force-push и требовать проверку
  перед слиянием.
- **Ротация ключей**, если они когда-либо пересылались в мессенджере или почте.
- **Рассмотреть приватный репозиторий.** Секретов в коде нет, но публичный код
  показывает всю логику проверок и упрощает поиск слабых мест.

## Тесты

```
node api/_telegram.test.mjs   # права владельца, 19 проверок
node api/_session.test.mjs    # сессии и изоляция данных, 15 проверок
node api/_settings.test.mjs   # режим обслуживания, 17 проверок
```

В каждом наборе есть проверка ровно той атаки, которая работала до
исправления, — чтобы регрессия была видна сразу.
